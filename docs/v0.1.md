# FWA V0.1 vertical slice

## Scope decision

V0.1 proves the engineering spine from a human Goal to a reversible project
revision. It deliberately accepts a human-authored DAG; automatic planning is
not required. Unity support is compile and EditMode-test evaluation, while
runtime control and playable evidence begin in V0.2.

The original specification called the concept “FW Agentic” and used illustrative
`fw` commands. The implemented standalone component is named FWA and owns the
`fwa` CLI and `.fwa` state directory. This naming keeps it independent from the
optional `fw` runtime and `fwe` editor.

The version is successful only when this chain is executable and inspectable:

```text
Goal
→ validated manual DAG
→ ready valid Node
→ isolated Git worktree
→ replaceable executor, including Codex
→ immutable Run and ChangeSet
→ compile/test evaluation and Evidence
→ accept or reject
→ exact or regression-gated integration
→ ProjectRevision and Ref versions
→ precise stale propagation
→ regression-gated revert as a new ChangeSet
→ downstream stale propagation with history preserved
```

## Definition-of-done mapping

| # | Required outcome | V0.1 implementation |
|---:|---|---|
| 1 | Create a Goal | `FwaApplication.createGoal`, `fwa goal create` |
| 2 | Produce or accept a DAG | human-authored JSON plan |
| 3 | Validate the DAG | strict schema, unknown-field rejection, Ref checks, cycle and dependency checks |
| 4 | Resolve ready Nodes | deterministic serial readiness projection |
| 5 | Isolate work | detached Git worktree per Run/Evaluation |
| 6 | Invoke Codex | `CodexExecutor`, selected with `fwa run next --executor codex` |
| 7 | Record Run | append-only Run events and executor identity |
| 8 | Capture ChangeSet | immutable base/head/commits/paths/patch and execution artifacts |
| 9 | Compile/test | `CommandEvaluator`; Unity profile supplies compile and EditMode checks |
| 10 | Store Evidence | content-addressed immutable artifacts plus projected Evidence |
| 11 | Accept or reject | evaluator-derived verdict; executor cannot self-accept |
| 12 | Integrate | direct exact-base or isolated two-parent merge with compile/test gate |
| 13 | Update Refs | only physically changed produced Refs advance |
| 14 | Mark stale | already-materialized consumers and transitive outputs are invalidated; unrun consumers are not |
| 15 | Inspect history | `status`, `events`, `verify`, public projection API |
| 16 | Revert | isolated revert candidate, compile/test gate, CAS promotion, new revert ChangeSet |
| 17 | Stale after revert | precise Ref consumers or conservative legacy DAG dependants; completed affected Goals reopen |

## Required inputs

The target must be a local Git repository. V0.1 commits, refs, worktrees, merge
parents, and promotion protocols are Git-specific application contracts;
substituting another version-control model is not a drop-in adapter change.
Its ignore rules must exclude
`.fwa/**`. Git needs an identity capable of creating Run, merge, and revert
commits. Node.js 20.10.0 or newer is required.

A complete ordinary-Git example, with all input files generated and both API
and CLI paths executable, is in [`getting-started.md`](getting-started.md).
It requires no Unity installation or model credentials.

A logical Ref is registered before any plan that names it. This example digest
is SHA-256 of the exact UTF-8 bytes `export const value = 0;\n`; generate the
digest for your actual initial source instead of copying an unrelated token:

```json
{
  "id": "ref://code/counter",
  "kind": "code",
  "uri": "counter.mjs",
  "version": "initial",
  "hash": "sha256:f8ff18e7dea68bb8dd4181fa54e8c2401abc2aae9008c0f7595483eb6a2074ec",
  "metadata": {}
}
```

A minimal plan is:

```json
{
  "schemaVersion": 1,
  "nodes": [
    {
      "id": "implement-counter-step",
      "dependsOn": [],
      "reads": ["ref://code/counter"],
      "writes": ["ref://code/counter"],
      "capabilities": ["code_edit", "shell"],
      "acceptance": { "checks": ["compile", "tests"] },
      "budget": {
        "maxRetries": 1,
        "maxFiles": 8,
        "maxDiffLines": 1000,
        "wallTimeMinutes": 20
      }
    }
  ]
}
```

The Codex input is explicit and versioned:

```json
{
  "schemaVersion": 1,
  "prompt": "Implement only this Node's bounded change and run focused checks.",
  "model": "gpt-5.5"
}
```

The optional `ignoreUserConfig: true` bypasses user configuration for that
invocation. On Windows, `windowsSandboxOverride: "elevated"` is a separate,
explicit privilege-expanding opt-in. It is rejected on other platforms and no
other override string is accepted.

## CLI flow

```powershell
node .\bin\fwa.js init --project D:\Git\my-game
node .\bin\fwa.js goal create "Add a small gameplay feature" --project D:\Git\my-game --json
node .\bin\fwa.js ref register .\counter-ref.json --project D:\Git\my-game
node .\bin\fwa.js plan load <goal-id> .\plan.json --project D:\Git\my-game
node .\bin\fwa.js run next .\codex-input.json --executor codex --project D:\Git\my-game --json
node .\bin\fwa.js evaluate run <changeset-id> .\acceptance-profile.json --project D:\Git\my-game --json
node .\bin\fwa.js integrate gated <changeset-id> .\regression-profile.json --target main --project D:\Git\my-game --json
node .\bin\fwa.js status --project D:\Git\my-game
node .\bin\fwa.js events --project D:\Git\my-game
node .\bin\fwa.js verify --project D:\Git\my-game
node .\bin\fwa.js revert run <changeset-id> .\regression-profile.json --target main --project D:\Git\my-game --json
```

An integration or revert regression profile must contain at least one check
with `kind: "compile"` and one with `kind: "test"`. Candidate promotion never
runs before both pass.

Recovery commands are separate because they can mutate durable or Git state:

```powershell
node .\bin\fwa.js run reconcile --project D:\Git\my-game
node .\bin\fwa.js evaluate reconcile --project D:\Git\my-game
node .\bin\fwa.js integrate reconcile --project D:\Git\my-game
node .\bin\fwa.js revert reconcile --project D:\Git\my-game
```

If a gated compile/test evaluator was interrupted without proving that its
process tree stopped, Integration or Reversion reconciliation remains fenced
and retains the detached evaluation worktree. Only after independently
confirming that every evaluator process has stopped may an operator run:

```powershell
node .\bin\fwa.js integrate reconcile --confirm-processes-stopped --project D:\Git\my-game
node .\bin\fwa.js revert reconcile --confirm-processes-stopped --project D:\Git\my-game
```

This flag is an operator assertion, not Evidence. FWA verifies and removes only
the owned worktree at the exact durable candidate revision, then records the
interrupted operation as failed. It does not resume evaluation or promote the
candidate. Without the flag, the recovery fence remains in place.

## State semantics

`produced`, `accepted`, `integrated`, and `valid` answer different questions.
An accepted Node may be stale. A reverted source Node is accepted historically,
has `validity=invalid`, and has `integrationStatus=reverted`. Its original Run,
Evidence, ChangeSet, Integration, candidate, and ProjectRevision remain visible.

DAG execution prerequisites and Ref data validity are separate checks. Reverting
a prerequisite blocks dependent execution/evaluation even when no declared Ref
read became stale. Ref invalidation follows explicit declarations and does not
enforce complete filesystem-read isolation or detect every external file edit.
The initial `Ref.hash` is a version token; see the generation and drift limits
in [`architecture.md`](architecture.md#effects-and-logical-refs).

`fwa node retry <node-id>` / `app.retryNode({ nodeId })` requeues a rejected Node
for retry, or a stale/invalid produced or accepted Node for recomputation. It
does not start an executor. Historical attempts and Evidence remain, the
existing attempt budget does not reset, and the next Run freezes current Refs.
Dependency, target, active-operation, and workspace-cleanup checks still apply.
The complete retry sequence is in [`getting-started.md`](getting-started.md).

Physical merge or revert conflicts are terminal, structured records and never
move the target. Regression failure preserves the candidate and Evidence but
does not move the target. Ambiguous post-promotion failure becomes
`recovery-required` and blocks further mutating operations until reconciliation.

## Verification obligations

V0.1 regression coverage must keep the following distinct:

- syntax/static checks;
- domain and replay tests;
- real Git worktree, merge, conflict, CAS, revert, and recovery tests;
- process-scoped Git fsmonitor isolation and Windows partial-remove cleanup
  tests, including registration, link, and directory-identity failure cases;
- real Codex CLI process invocation and mutation in an isolated workspace;
- real Unity batch compile, EditMode execution, parseable NUnit XML, and result
  validation;
- one retained live composition run bound to the current FWA source digest and
  covering the 17-step success path;
- package boundary and dry-pack inspection.

Passing one category is not evidence for another. The frozen completion
snapshot and its environmental limitations are recorded in
`docs/v0.1-validation.md`; that historical record is not a claim that later
source changes have received the same live or full-suite validation.

## Non-goals

V0.1 does not claim an automatic planner, vector/embedding/RAG knowledge
system, multi-agent or reviewer swarm, parallel executor scheduler,
authenticated approval service, production sandbox, FWE adapter, FWE UI, or a
shared FWA/FWE configuration contract. It also excludes Unity runtime control,
PlayMode scenarios, screenshots/video/telemetry, semantic or behavioral merge
analysis, caching, automated game design or gameplay AI, learning, cloud or
distributed operation, a web dashboard, and multi-engine support.
