# 需求、DAG 与节点收束

FWA 的主界面只有一个工作台：输入需求，生成 DAG，选择节点查看结果或补充要求，然后继续执行。图一直保留；执行、验证、证据和采用记录都属于相应节点，不再通过基础/高级菜单或阶段页面来回切换。

已有任务时，“新建任务”默认收起；空项目直接展开。它创建新任务，不修改当前需求。未提交内容保留草稿提示，规划失败或需要补充信息时展开对应请求。顶部只显示一次完成比例和当前下一步：恢复、正在处理、可继续执行或查看已有结果。只读权限单独标识，不掩盖真实中断原因。

节点详情优先显示结果、状态和当前可做的操作。验收条目与执行记录按需展开，依赖可直接打开。“调整此任务”用于修订所选节点；已有操作尚未结束时只暂存补充要求。轮询刷新保留草稿、展开项和画布视角。窄窗口把详情放在图下方，避免压缩节点。

“全部目标”不预选节点；点击节点后切到所属目标，“继续”只推进该目标。当前节点修订后跟随同一逻辑成果的新版本；拆成多个成果时显示该目标的完整图，不代选某个子节点。单独打开的历史记录仍保留历史详情，同时展示当前任务图。

## 节点与连线

- 节点代表一个可独立检查的用户结果。标题说要得到什么，`outcome` 说明可观察结果，`acceptance` 保存完成条件；具体工作写入 `instruction`。
- 小需求通常只需一个完整成果节点，包含实现与检查；大需求先形成少量成果，确有需要再派生。规划、审查、验证、集成本身不生成占位节点；检查归属它验证的成果。只有用户确实需要交付的工具或报告才成为独立节点。
- `dependsOn` 只表达需要消费的前置结果。`dependencyReasons: [{nodeId, reason}]` 必须和依赖一一对应，说明用到什么、为什么需要等待。
- 共同写文件或占用同一工具不构成业务依赖。调度器按写范围和 `resources` 临时串行执行。
- 分组只用于组织和汇总完成情况，不增加依赖，也不执行。旧计划仍可读取；没有记录理由的旧连线如实显示未记录，不自动猜测或删除。
- 新规划不能以不同名称重复同一成果、工作指令、验收与读写范围，也不能创建没有写入范围的执行节点。已有历史定义仍可读取。相似标题、共享检查或传递可达本身不证明节点或连线多余，不据此自动删除。

规划前自动提供有界的真实项目路径清单，避免仅凭目录惯例猜测现有文件。扫描不读文件正文、不跟随链接，跳过框架、内部状态和常见依赖/缓存目录；数量、深度和完整清单大小都有限额。截断或读取异常会明确标识，未列出的路径不能视为不存在。规划证据保存实际清单和摘要，摘要只绑定路径清单，不证明文件内容。已有检查配置的工作目录及期望产物也会完整传给规划器。

能力不足时，问题应说明缺少的运行入口、环境或采集方式，不让用户填写内部检查编号。视觉或交互验收仍须真实运行证据，但不会默认增加需求之外的前后对比录制步骤。

## 派生与修订

补充节点要求后，版本化修订更新图。新派生节点用 `derivedFrom` 指向原逻辑节点，保留来历。

后续修改子节点时，即使来源已被拆分替换、退出当前图，也保留原来源标识；不会重新加前缀或改连其他来源。只更新受影响的节点，无关分支不重复创建。

- 只允许拆分从未执行过的来源；同一来源历史累计最多 8 个子结果。已尝试节点沿用原逻辑身份修复，不能重置失败预算。
- 每个子结果必须具体且不同。保留来源时，子结果必须通过真正的依赖供来源使用；替换来源时至少有两个子结果，并完整覆盖原验收条件、明确连接原来的消费者。
- 原有前置也必须通过派生结果保持可达。将边连到实际消费该前置的子结果，允许经其他子结果间接消费；不能静默丢掉前置，也不要求每个子结果都连全部前置。新修订严格检查，旧事件按原规则回放，不追改历史。
- 不能分割无法证明覆盖的命名验收合同，不能删除既有执行历史。无关分支保留原版本和结果。
- 不添加专门的“收束节点”。真实成果采用后自然完成，分组和目标按真实结果汇总。

非空描述和逐边对应关系可以机械校验；描述是否正确反映用户需求仍需要规划质量与用户检查。这里没有宣称字符串检查能证明业务依赖合理。

## 执行与收束

同一批最多执行 4 个可并行节点。Workbench 先按真实 Ref 路径、读写范围和独占资源筛选，再应用数量上限，避免排在前面的冲突任务挡住后面的独立工作。预选保守地按大小写不敏感比较路径；核心调度器仍在实际 Git 配置和原子准入边界复核。预选只决定本次准备哪些输入，不授予执行权限；大小写敏感项目中仅大小写不同的路径可能仍被保守串行处理。

`workflow.work` 会处理已有候选，再执行可运行的节点。配置真实验证命令后，普通执行或验证失败会在同一次请求中自动续修：保留失败候选与完整证据，向执行器提供候选版本、最多 8 KiB 的失败日志摘录和实际检查命令。同一基线下，框架先校验最近失败候选的归属、Git 对象、产物与完整写入范围，再恢复到新工作树；执行器直接修改已恢复的文件。主分支和新 Run 基线不变，旧实现与本次修复一起计算范围、文件数和差异预算。正式验证仍独立执行。

目标基线已变化时，框架明确报告未自动恢复，由执行器结合新基线读取旧候选、保留有用修改。候选损坏、范围不符或恢复中收到反馈/中止信号时，不启动后续模型调用；恢复错误属于基础设施检查边界，不反复当作代码错误重试。成功执行证据保留 `repairRestoration`，注明实际恢复或基线变化。已通过的节点不会重新制作；重新发起 Work 也会从保留的候选或拒绝结果继续。

续修沿用原尝试预算。相同代码与失败连续出现两次时停止，新的运行编号、日志引用或心跳不算进展。零修改、缺检查配置、待处理反馈、独立评审、超时或进程/工作区状态不明确都会明确停下；一条分支被拒绝不会重复派发并阻塞其他独立分支。界面在真实续修 Run 运行时显示“正在修复”。控制器进程崩溃后的核对与恢复仍是显式操作，页面刷新或旧 command ID 回放不会自动接管未知进程。

工作台内置规划器每次调用默认最多三分钟，执行器每次调用默认最多三十分钟；持续日志不会重置总时限。超时停止并保留已有记录，只有确认进程已退出才释放执行边界。可信程序启动参数 `workflow.codexOptions.timeoutMs` 可覆盖两者，`null` 或 `0` 显式关闭总时限；注入适配器及直接使用底层执行器仍沿用各自配置。这不是整个目标的总预算，原节点时间预算也继续独立生效。

工作台顶部的“继续”推进当前目标，节点不再另设执行按钮、检查配置选择或手动验证步骤。文件差异在节点内按需展开，展开前不读取差异内容。

受信启动配置中的 `completionPolicy: {"mode":"automatic","manualProfiles":[]}` 允许验证通过的节点自动运行集成回归、采用，并继续已解锁的后继。自动确认单独记录为策略决定，绑定确切候选、证据、检查配置与策略，不能冒充用户确认。`manualProfiles` 列出的检查合同仍需人工确认；不配置此字段的旧项目保持人工确认语义。

需要人工判断时，节点显示“确认并继续”。这一次操作对应 `workflow.finish`：记录绑定当前候选及证据的真实确认，运行集成回归并采用，再继续当前目标，直到下一处需要人工确认、失败或预算边界。它复用持久化任务、校验令牌、租约和 Git 边界；重复提交同一命令不会重复执行。采用失败时已有确认和候选保留，刷新后可继续采用。

只有当前候选同时满足 **accepted、valid、integrated 到目标分支**，节点才完成并解锁后继。可信程序适配器仍可自动采用，但返回成功必须有实际集成事实。未配置验证能力的图可以查看和规划，编辑器在执行前说明缺失配置。

这次界面与协议调整不会重新规划或执行历史工程。老任务的复杂拆分和连线保留原始记录；新规划使用上述规则。

## 回归验证

`node --import ./tools/test-environment.js --test --test-concurrency=1 test/workbench-auto-flow.test.js` 在临时 Git 工程验证自动依赖链、人工确认后续跑和重启后的幂等回放。浏览器闭环使用 `node tools/check-auto-flow-browser.mjs --fwe <FWE目录> --playwright <playwright/index.mjs> --output <报告目录>`，需要本机 Edge；它检查真实 HTTP、节点内差异、两种收束策略及实际集成结果，不调用模型或运行用户游戏。

`node --import ./tools/test-environment.js --test --test-concurrency=1 test/workbench-repair-flow.test.js test/workbench-repair-boundaries.test.js` 验证失败后自动修复、真实 Git 集成及依赖推进，以及预算、无进展、反馈竞态和指定节点范围。执行器是可控测试适配器，不能代替真实模型长任务的完成率测量。

`node tools/check-planner-quality.mjs --output <报告目录>` 是显式的真实模型规划评测，不属于普通单测。四个合成工程覆盖完整交付、独立需求、真实产物依赖及缺少触控验收能力；最多两个并发、每例三分钟、没有自动重试，也不会派发执行。报告记录真实输出、规划证据和只读检查；预期只给评审者，不喂给模型。通过结构检查不代表语义正确，必须另行核对成果覆盖、依赖理由和验收能力。

`node tools/check-planner-revisions.mjs --output <报告目录>` 进一步检查两类需求的局部反馈与多轮派生，最多五次模型调用，每次三分钟硬时限；单例失败即停，不自动重试。`check-workbench-revisions-browser.mjs` 使用与上面浏览器工具相同的参数，在真实页面验证跨目标选择、修订跟随、历史链接与拆分后的总览，业务 Run 保持为零。
